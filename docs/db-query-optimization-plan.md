# 릴리스 후 DB·쿼리 최적화 계획

## 원칙 및 운영 경계

운영 DB 제한과 초기화·연결 오류 진단은 [배포 설정](deployment.md)에 따라 구현되어 있다. 아래 쿼리·클라이언트 캐시 정책은 실측 후 진행할 후속 작업이다. 현재 관리자 개요는 서버 메모리 캐시를 사용한다.

- Supabase를 운영 데이터 저장소로 사용한다. 로컬 JSON fallback은 명시적인 local/test 모드에서만 허용한다.
- Supabase가 설정된 production에서 연결·쿼리가 실패하면 fallback으로 전환하지 않고 fail closed한다. 오류 코드, 대상 경로, correlation ID, 재시도 가능 여부를 포함한 실행 가능한 진단을 기록·반환하되 비밀은 노출하지 않는다.
- 최적화 전후 동일 시나리오에서 요청 수, DB 쿼리 수, 중복 요청 수, 조회 행 수, p50/p95 지연시간을 측정한다.
- 측정으로 병목이 입증된 경로만 변경하며, 인증·권한·데이터 신선도를 성능보다 우선한다.

## 1. 기준선과 go/no-go

릴리스 버전에서 아래 시나리오를 각각 최소 30회, 고정된 인증 상태·데이터 규모·페이지 크기로 측정한다.

- 초기 페이지 로드의 health/session/protected-data 요청
- `GET /api/admin/overview?userPage=1&userPageSize=25`
- `GET /api/pantry`
- `GET /api/recommendations?limit=8`
- 익명·인증 추천 요청

요청별 쿼리 목록, `select=*` 여부, 조회 행 수와 p50/p95를 기록한다. p95가 목표 초과, 중복 요청·쿼리 발생, 필요 행의 2배 초과 조회, 불필요한 전체 테이블 조회 중 하나가 확인될 때만 다음 단계로 진행한다. 기준선과 판정이 없으면 변경하지 않는다.

## 2. 입증된 병목의 최소 수정

필요한 열·사용자·페이지·limit만 조회하고 관리자 목록은 페이지네이션과 명시적 집계를 사용한다. 변경 후 같은 시나리오를 재측정한다.

- go: 요청·쿼리 수가 증가하지 않으며 p95가 20% 이상 개선되거나 과다 조회 행이 50% 이상 감소한다.
- no-go: p95가 10% 이상 악화되거나 인증·권한·정합성 회귀가 1건이라도 발생한다. 해당 변경은 즉시 롤백한다.

## 3. 클라이언트 전용 단기 캐시

쿼리 수정 뒤에도 중복 요청이 남고 기준선 대비 개선 여지가 있을 때만 브라우저 메모리에 캐시한다. 서버 프로세스 캐시는 이 단계에 도입하지 않으며, 페이지 수명과 프로세스 수명을 혼용하지 않는다.

- 키는 `health`, `session`, `pantry:{userId}`, `recommendations:{userId}:{limit}`처럼 사용자 범위를 명시한다. 사용자 식별이 없으면 사용자별 캐시를 사용하지 않는다.
- health는 클라이언트 메모리에서 최대 30초, session은 해당 페이지 수명 동안만 유지한다.
- pantry·recommendations는 클라이언트 메모리에서 사용자별 최대 30초 유지한다. 로그아웃 또는 401에서 해당 사용자 캐시를 삭제한다.
- pantry 생성·수정·삭제 성공 후 `pantry:{userId}`를, 추천 성공 후 해당 recommendations 키를 무효화한다.
- 토큰·비밀번호·개인정보를 `localStorage`나 `sessionStorage`에 저장하지 않는다.
- 캐시는 탭·브라우저 인스턴스별로만 유효하며 서버 인스턴스 간 공유되지 않는다. 향후 서버 캐시가 필요하면 공유 저장소와 명시적 무효화·일관성 설계를 먼저 승인한다.

캐시 전후 stale 응답, 사용자 간 혼재, 무효화 누락을 확인한다. 적중률이 20% 미만이거나 p95가 10% 이상 개선되지 않으면 no-go로 제거한다.

## 4. 실행 계획 기반 DB 변경

목표 미달 쿼리에 한해 실행 계획과 실제 실행시간을 수집한다. 계획에서 병목이 확인된 경우에만 사용자·날짜 조건 인덱스 또는 반복 집계·페이지 비용을 줄이는 RPC/view를 검토한다. 변경 전후 실행 계획, p95, 읽은 행 수와 쓰기 비용을 기록하며 유의미한 개선이 없거나 비용·복잡도가 늘면 적용하지 않는다.

## 5. 구조 변경 보류

React/Vue/Svelte/Vite 등 프레임워크 마이그레이션은 보류한다. 쿼리와 캐시 최적화 후에도 측정된 요청량 또는 유지보수 비용이 지속적으로 목표를 초과할 때 별도 제안으로 검토한다.

## 집중 검증 및 롤백

각 단계의 동일 시나리오에서 요청·쿼리 수, p50/p95, 행 수와 결과 정합성을 재검증한다. 인증·권한 오류, 데이터 노출, 무효화 실패, p95 10% 이상 악화, 요청·쿼리 증가, 개선 목표 미달 또는 비용 증가가 있으면 배포하지 않고 마지막 정상 변경으로 롤백한다. 결과에는 시나리오, 표본 수, 기준선·변경 후 수치, go/no-go와 롤백 여부를 남긴다.
