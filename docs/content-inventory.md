## DB 대조

`data/app.db.json`은 로컬 테스트·개발 상태를 집계만 읽었다. 원본의 계정, 세션, 게스트 토큰, 로그 ID와 같은 값은 이 문서에 기록하지 않는다.

| 항목 | 로컬 개수 |
| --- | ---: |
| schemaVersion | 2 |
| users | 2 |
| sessions | 2 |
| ipBlocks | 0 |
| pantryItems | 2 |
| recommendationLogs | 12 |
| savingsLogs | 0 |
| guestSessions | 14 |
| userShortcuts | 0 |
| menuSelections | 2 |
| mergeTransactions | 2 |
| mergeTransactionSteps | 6 |

로컬 보관 재료 이름은 `계란` 하나였고 수량 표기는 `2개`였다. 추천 스냅샷에 확인된 재료 이름은 `계란`, `김치`였다. 추천 기록은 메뉴·입력 스냅샷이지 카탈로그의 정본이 아니다. 부모 에이전트가 별도로 확인한 운영 Supabase는 13개 테이블, `pantry_items` 1건의 `계란`, `recommendation_logs` 11건, `menu_selections` 0건이며 독립 레시피 마스터 테이블은 없다. 운영 수치와 로컬 JSON 수치는 서로 다른 상태이므로 합산하지 않는다.

스키마상 `pantry_items`는 사용자 또는 게스트가 보유한 재료이고, `recommendation_logs.ai_response`와 `menu_selections.recipe_snapshot`은 당시 응답을 보존하는 스냅샷이다. 정적 카탈로그와 새 레시피 사양을 바꿔도 과거 스냅샷은 덮어쓰지 않아야 한다.

## 현재 코드의 연결 지점

- [`public/food-catalog.js`](../public/food-catalog.js)는 브라우저와 서버가 함께 읽는 정적 48개 카탈로그다. `flattenCatalog`, `findCatalogItem`, `ingredientNamesMatch`가 목록·상세·추천의 공통 조회 계약이다.
- [`public/recipe-specs.js`](../public/recipe-specs.js)는 명시적 144개 레시피 사양이다. 2026-09-13 현재 Sol의 전체 메뉴 내용 텍스트 대조가 완료됐고 조리 시험은 수행하지 않았다. 상세 페이지가 `food-catalog.js`의 합성 프로필을 직접 사용하지 않고 이 사양을 사용하며, `item.id:0..2` 누락·팬텀 키를 검사해야 한다.
- [`public/app.js`](../public/app.js)는 카테고리 탐색, 입력 폼, 서버 추천 렌더링을 담당한다. 카테고리에서 `./ingredient.html?id=<id>`로 이동하고, 카탈로그 추천은 보유·부족 필수 재료를 나누어 표시한다.
- [`public/ingredients.html`](../public/ingredients.html)와 [`public/ingredients.js`](../public/ingredients.js)는 48개 목록, 이름·별칭·분류·메뉴명 검색, 상세 링크를 제공한다. [`public/ingredient.html`](../public/ingredient.html)과 [`public/ingredient.js`](../public/ingredient.js)는 `id` query를 조회해 보관 정보와 3개 메뉴를 렌더링하고, 알 수 없는 ID에는 돌아가기 링크를 표시한다.
- [`server.js`](../server.js)의 `POST /api/recommend`는 입력과 DB 보유 재료를 별도로 검사하고 AI 또는 정적 fallback을 선택한다. 이 경로의 `normalizeRecommendation`와 fallback도 레시피 필수 재료 계약을 따라야 한다. DB에는 정적 카탈로그를 저장하지 않는다.

## 콘텐츠 품질 이슈 (교체 전 역사적 조사)

아래는 명시 사양으로 교체되기 전의 `food-catalog.js` 합성 경로에서 확인한 문제를 남긴 역사적 조사 기록이다. 현재 결함 목록으로 읽지 않으며, 당시 구조적으로는 48개·144개가 나오지만 `requiredIngredients`가 재료와 `extraIngredients`만 합쳐 제목에 필요한 재료를 빠뜨리고, 메뉴명에 맞는 조리 단계를 넓은 정규식 하나로 골랐다. 현재 사양의 144개 전체 메뉴 내용 텍스트 대조는 Sol이 2026-09-13 완료했으며 조리 시험은 수행하지 않았다.

### 필수 재료 누락

- 밥·덮밥·비빔밥·주먹밥·볶음밥·쌈밥 메뉴가 밥을 필수로 선언하지 않는다. 확인한 예는 `돈가스덮밥`, `떡갈비덮밥`, `야채계란볶음밥`, `참치마요덮밥`, `스팸마요덮밥`, `스팸김치볶음밥`, `계란카레밥`, `계란짜장덮밥`, `깍두기계란밥`, `열무계란비빔밥`, `장조림버터밥`, `장조림계란덮밥`, `장조림주먹밥`, `멸치주먹밥`, `멸치계란볶음밥`, `멸치고추장비빔밥`, `진미채마요덮밥`, `진미채주먹밥`, `진미채계란밥`, `콩나물비빔밥`, `단무지참치주먹밥`, `단무지마요밥`, `꼬마김밥식 비빔밥`, `무말랭이참치밥`, `무말랭이주먹밥`, `계란상추쌈밥`, `깻잎참치덮밥`, `깻잎간장비빔밥`, `깻잎주먹밥`, `김치계란볶음밥`이다.
- `김치계란덮밥`은 김치·계란, `간장버터계란밥`은 계란, `계란카레우동`은 계란을 제목과 설명에 맞게 필수로 가져야 한다. `또띠아피자`는 토마토소스와 치즈, `치즈컵밥그라탕`은 모짜렐라치즈, `너겟토스트`는 치즈, `돈가스샌드`는 소스가 필요하다.
- `간단떡국`은 대파를 쓰는 설명과 필수 목록이 어긋난다. `어묵떡볶이`와 `라볶이`는 떡·어묵 또는 키트만으로는 양념이 완성되지 않으며, `비빔만두`는 초고추장 또는 동등한 소스를 선언해야 한다.
- `야채크림파스타`는 우유·크림, `닭가슴살파스타`는 소스, `닭가슴살랩`은 채소, `닭가슴살볶음밥`은 냉동야채를 제목·설명과 함께 필수 또는 명시적 선택으로 정리해야 한다. `양파핫소스피자`, `골뱅이무침밥`, `골뱅이양배추무침`도 제목에 있는 핫소스·무침 양념을 누락하지 않는다.
- [교체 전 이슈] 별칭이 `치즈`인 카탈로그 재료와 `모짜렐라치즈` 사양은 당시 `ingredientNamesMatch`에서 같은 것으로 보장되지 않았다. 필수·보유·부족 계산에서 `모짜렐라치즈`가 선택 재료로 중복 표시될 수 있었고 서버의 단순 `ingredientKey`도 카탈로그 별칭을 몰랐다. 현재는 `ALIASES`와 `ingredientAliases`가 양쪽 입력을 같은 별칭 그룹으로 확장하므로 대표명↔별칭과 별칭↔별칭을 모두 해결하며, `ingredientNamesMatch`는 계란/달걀·김치/배추김치·우동/냉동우동·밥/즉석밥 같은 동등 이름을 매칭하고 unrelated food는 합치지 않는다.

### 조리법 프로필 불일치

- `치즈감자구이`가 `감자구이`라는 문자열 때문에 토스트 프로필을 택해 “빵이나 또띠아”를 요구한다. 감자는 전자레인지·오븐·에어프라이어로 익히고 치즈가 녹는 기준을 제시해야 한다.
- `프렌치토스트`는 계란·우유에 빵을 적시는 단계가 없고 일반 토스트 단계만 있다. `우유계란찜`은 프라이팬 오믈렛 단계로 생성되지만 덮어서 찌거나 전자레인지로 익히는 계란찜이어야 한다.
- `김치볶음우동`은 `우동` 분기가 먼저라 국물 면 단계가 된다. 익힌 우동과 김치를 팬에서 볶는 단계가 필요하다. `볶음밥오믈렛`도 볶음밥을 만든 뒤 계란으로 감싸는 단계가 빠진다.
- `장조림버터밥`은 `장조림` 때문에 조림 프로필을 타며 새 양념물에 다시 졸인다. 익힌 장조림을 찢어 밥·버터와 섞는 메뉴로 분리해야 한다.
- `토마토파스타`, `닭가슴살파스타`, `닭가슴살파스타`, `야채크림파스타` 등 파스타 메뉴에 면 삶기와 소스 유화 단계가 부족하다. `어묵떡볶이`, `비빔만두`, `치즈컵밥그라탕`도 각각 소스에 끓이기, 만두를 굽고 버무리기, 치즈를 녹이는 고유 단계가 필요하다.
- `요거트볼`과 `바나나요거트`는 차갑게 섞는 메뉴여야 한다. 모든 냉장 식품에 볶기 단계를 적용하지 않는다. `비빔국수`는 면을 삶은 뒤 찬물에 헹구고 양념에 버무리는 차가운 면이며 뜨거운 국물 프로필이 아니다.

### 보관·표시와 서버 계약

- `떡갈비`, `어묵`, `떡볶이키트`, `떡국떡`은 현재 분류·제품 상태에 비해 보관 문구가 일반 냉장 문구로 남을 수 있다. 냉동·냉장·상온 여부는 상품 포장을 우선하도록 재료별 안내를 명시한다. `깍두기`도 김치류 냉장 안내에서 빠지지 않아야 한다.
- `모짜렐라치즈`의 양이 치즈 기준량으로 처리되지 않는 경우가 있고, 합성 메뉴의 시간·분량은 실제 검증값이 아니다. 모든 상세 레시피에 1인분 응용안과 제품 표시 우선 문구를 유지한다.
- 서버 fallback은 카탈로그를 사용하도록 바뀌었으나, 최종 응답에서 `ownedIngredients`, `inputIngredients`, `missingIngredients`가 서로 겹치지 않는지와 제목 필수 재료를 다시 검증해야 한다. 희망 시간이 짧다고 조리 단계나 실제 시간을 숫자로만 줄이지 않는다.
- DB 확인은 서버의 일반화 키와 브라우저 카탈로그 별칭이 다르다. `계란`/`달걀`, `냉동우동`/`우동`, `배추김치`/`김치` 같은 입력을 같은 정책으로 판정하거나 차이를 사용자에게 표시한다.

## QA 계약

정적 모듈 검사는 `FOOD_CATALOG`의 48개 안정 ID, 각 3개 메뉴, 명시 사양의 144개 `item.id:0..2` 키가 정확히 일치하는지 확인해야 한다. 각 사양에는 필수·선택 재료의 이름과 양, 도구, 순서가 3단계 이상, 완료 기준, 1인분, 출처 범위와 추정 시간 표시가 있어야 한다. 메뉴명에 필요한 재료가 필수 목록에 있고, 같은 재료가 보유·부족에 동시에 나오지 않아야 한다. 별칭의 raw/cooked 입력, 차가운 요거트, 프렌치토스트 불림, 계란찜 찜 조리, 차가운 비빔국수, 감자구이의 빵 오인 여부를 행위로 검증한다.

브라우저 검사는 격리된 임시 DB로 수행한다. `ingredients.html`에서 48개 카드, 별칭·메뉴명 검색, 검색 결과 없음이 동작하고 각 `ingredient.html?id=<id>`가 오류 없이 3개 메뉴를 렌더링해야 한다. 알 수 없는 ID와 `<script>alert(1)</script>` query는 안전한 오류 또는 이스케이프 결과여야 한다. 메인 카테고리와 내 정보 링크, 360×800 및 390×844에서 수평 overflow와 콘솔 오류를 확인한다. 기존 API·PWA·DB 계약 테스트와 모바일 흐름은 실제 로컬 또는 운영 DB를 사용하지 않는 격리 설정으로 실행한다.
